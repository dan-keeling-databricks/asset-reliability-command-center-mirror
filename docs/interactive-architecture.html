02 · Agent runtime

Autonomous by trigger, not by prompt

The user does not ask “what is happening?” The threshold crossing already contains the asset and condition. The App creates a machine-authored investigation request and starts one isolated async task per incident.

01 / TRIGGER

The plant state starts the work

Every second, the App evaluates current Lakebase state. A threshold entry transactionally creates one incident and one run for the scenario, pump, and rule.

  • Asset, condition, timestamp, and incident ID supplied automatically
  • Duplicate incident creation is constrained in Lakebase
  • Normal transients can run in parallel
02 / DISCOVERY

Procedure and tools arrive at runtime

The runtime first loads the current Unity Catalog Skill, then asks the MCP service for its tool surface. The UI renders those events only after discovery.

  • No hardcoded UI stages or expected Skill name
  • No fixed sequence or tool-call cap
  • Every actual call becomes a timeline event
03 / OUTCOME

Evidence decides the branch

Self-resolving transients close with no action. Persistent, correlated degradation drives preparation and a governed work-order attempt.

  • Decision rationale is prospective—before calls execute
  • Terminal output uses Finding, Evidence, Risk, Action
  • ASK creates a pause, not a premature conclusion

Reasoning is code-defined; tool choice is model-driven.

The current main runtime begins with GPT-5.1 for tool selection and routes subsequent reasoning to Claude Sonnet 4.5 when the governed risk tool establishes high risk. Model endpoint names appear in the UI only after a real model event.

Exactly what the agent can reach

05 · Trust boundaries

Three identities, separated responsibilities

The model never receives broad workspace credentials. The App’s infrastructure access and the operator’s governed business identity are distinct, and bearer tokens remain process-local.

U

Operator / OBO identity

The App receives a forwarded user token with the ai-gateway scope. It uses that identity for Skill and MCP Gateway calls.

  • Databricks AppCAN_USE
  • CatalogUSE_CATALOG
  • SchemaUSE_SCHEMA
  • UC SkillREAD_VOLUME
  • MCP serviceEXECUTE
A

App service principal

Runs FastAPI, the evaluator, the code-defined agent, and the source MCP server. App resource bindings define its infrastructure access.

  • Lakebase branchCAN_CONNECT_AND_CREATE
  • SQL warehouseCAN_USE
  • Model endpointsCAN_QUERY
  • Source App boundaryCAN_USE
  • Kafka networkNONE
J

Isolated job compute

Two continuous classic-compute jobs separate signal production from ingestion and from the interactive App.

  • Producer → KafkaPUBLISH
  • Producer → commandsCLAIM / ACK
  • RTM → KafkaREAD
  • RTM → LakebaseSTREAMING SINK
  • RTM checkpointUC VOLUME
Token boundary

The browser’s forwarded token is cached only in App process memory and used for Gateway calls. Lakebase stores the identity subject for audit, never the bearer token. A restart during pending approval therefore requires a live user session before replay can continue.

06 · Operational design

Fast reads as the event log grows

Lakebase holds both the append/upsert telemetry log and bounded operational projections. The dashboard does not scan history to repaint the fleet.

Live-state strategy

Canonical tables first; notifications are only hints.

On ingestA Lakebase trigger upserts pump_live_state and emits LISTEN/NOTIFY.
For displayThe App coalesces a notification burst for 50 ms, rebuilds one snapshot, and publishes a revision over SSE.
For alertsAn independent one-second loop queries current state and transactionally creates incidents on threshold entry.
For trendsEight index-backed lateral probes fetch at most 20 samples per pump, keeping work bounded.
For retentionBest-effort cleanup removes 24-hour-old telemetry in batches of 1,000 without blocking ingestion.
